## 1. UI refresh: the sci-fi boards, stripped back

Reference: `docs/art/scifi-*.png` (the sci-fi HUD boards and the minimal dark
variant). The target is a mix of the two: the minimal variant's calm and space,
with the sci-fi boards' details used sparingly.

**Look**

- Keep today's colour system. The accent follows the scene and the rank, as the
  title already does: the sky and area colours (`world/atmosphere.ts`,
  `world/palette.ts`) and the rank colours. Light mode (cream) and dark mode both stay.
  Don't introduce a fixed cyan; the boards' cyan stands for "the accent".
- **Sci-fi details only where they matter.** Cut-corner frames and a soft glow on
  the one main button per screen (fly, fly again, buy, claim) and on key cards
  (the ranked card, the results score). Use segmented meters for progress (level,
  rank XP, upgrade tiers, settings sliders), and hex icons for the dock.
- **Everything else is stripped back:** thin 1px lines, no frames around lists,
  generous spacing, the existing fonts (Host Grotesk, Geist Mono). Add no new
  font unless a display face for headings clearly helps; if you add one, use
  `@fontsource` and subset it to Latin.
- Build the frames, meters and hex icons as small reusable pieces: CSS classes in
  `ui/styles/` and helpers in `ui/`. Respect reduce motion, high contrast,
  colour-blind mode, larger text and the 44px tap areas. Check both themes.

**Flow** (`docs/art/scifi-flow.png`)

- **Hub:** one main fly button for the mode on show, with mode chips under it
  (ranked, solo, endless, daily, zen; only the ones the staged reveal has opened).
  Remember the last mode. The ranked card shows this week's best and league place.
- **Dock:** hangar, shop, goals, ranks (leaderboards and league) and record, as
  hex icons with a dot when something can be claimed. One tap from the hub to
  each; back returns to the hub.
- **Results:** score and best first; fly again as the biggest button; double
  credits and share under it; a rank XP meter. When this run's credits now buy an
  upgrade or a look in today's shop, add a line with one tap to it
  ("enough for thrust 4 · open hangar").
- **Pause and the revive offer:** framed modals over the frozen course, as on the board.
- **Hangar:** keep upgrades and looks together, with the ship on its platform
  above them; give upgrades meters and a price button.
- Keep every existing feature reachable; this is a re-layout, not a removal. Update
  the browser tests for any changed selectors, and add one for the results → hangar link.

Measure the title and a run before and after (frame time, DOM nodes; see
`docs/development.md`, "Measuring performance"). Glow (blur, shadow) must not cost
frame time in a run: no blur filters on HUD elements that change every frame.

## 2. Analytics: Firebase Analytics

**Setup.** Add Firebase Analytics through a Capacitor 8 plugin
(`@capacitor-firebase/analytics` is the usual choice; check it supports Capacitor
8), and only that package, checking `git diff package-lock.json` for churn. On the
web build, analytics is off. The plugin needs `google-services.json` in
`android/app/`. It's a config file, not a secret, but don't commit it: add it to
`.gitignore`, document where Tom gets it, and make the build work without it
(analytics off).

**Consent and privacy.**
- Analytics starts disabled. It turns on only once the player agrees, through the
  same consent flow AdMob already uses (UMP, `privacy-choices`), plus a
  "share usage stats" setting the player can turn off at any time.
- Send no personal data: no names and no emails. Use the Supabase user id as the
  user id only if Tom confirms; otherwise use Firebase's own app instance id.
- Update `public/privacy.html` (the Firebase Analytics section, what's collected,
  how to opt out) and `docs/play-console.md` (the Data safety answers that change:
  app activity and device IDs, for analytics, optional).

**Events.** A thin `platform/analytics.ts` with typed events, so call sites stay
one line and nothing is sent when it's off. Names in snake_case, within Firebase's limits.

- **Runs:** `run_start` (mode), `run_end` (mode, score, distance, seconds, level, crashed or finished).
- **Onboarding:** `tutorial_complete`, `tutorial_skip`.
- **Accounts:** `sign_up` (method: anonymous or google); a `login` with Google.
- **Ads:** `ad_offer_shown` (placement: revive, double_credits, daily_gift,
  goal_swap), `ad_offer_tapped`, `ad_rewarded`, `ad_skipped`, `ad_unavailable`.
- **Store funnel:** `view_store` (source: dock, short of credits, results link,
  hub card…), `view_item` (product), `begin_checkout` (product),
  `purchase` (product, value, currency, from the store result), `purchase_cancelled`.
  "Looked but didn't buy" is then the funnel view_store → purchase in Firebase.
- **Economy:** `spend_virtual_currency` and `earn_virtual_currency` (credits or cores; what for).
- **Screens:** `screen_view` for each screen as it opens.

**What Tom wants to see, and where it comes from:**

| Question | Source |
|---|---|
| How many people play; active now (day, week, month) | Firebase: active users, realtime |
| Retention (day 1, day 7, day 30) | Firebase: retention cohorts |
| Accounts ever; made in the last month; made in the last 6 months | Supabase: `players.created_at` (every install gets an anonymous account). Add a `security definer` view or RPC for the service role only, never `anon`, with a new migration, its `MADE` marker and a PGlite test |
| Ad offers shown vs watched | Firebase: the ad events; AdMob for revenue |
| Store views without a purchase | Firebase: the store funnel |

Write `docs/analytics.md`: what's tracked and why, how to set up the Firebase
project, which Firebase reports and funnels to build (step by step), the SQL for
the account counts, and how to link Firebase to Google Ads so the app campaign can
optimise for `tutorial_complete` or `purchase` rather than just installs.

## 3. A way to the store, and credit packs

**Credit packs (new products).**
- Add credit packs to `CONFIG.economy.store.products`, for example 5,000, 15,000
  and 40,000 credits. Price them against the current earn rate so a pack never
  makes ranked unfair: credits only buy looks and the upgrades anyone can earn,
  and leagues already group players by upgrades.
- Grant them through RevenueCat and the webhook as the core packs are granted,
  through the server (a new grant path or the `sync_credits` merge; credits must
  not be lost or doubled on a retry). Write SQL tests.
- List the exact Play Console product ids, names and prices for Tom to create.
- Keep the cores-to-credits swap as well.

**When the game suggests the store** (only when it helps):
- **Short of credits:** tapping an upgrade or look you can't afford opens a small
  sheet, "120 credits short", with three choices: swap cores for credits (if you
  have enough cores), buy a credit pack (the smallest that covers it, with its
  price), or not now.
- **Short of cores:** the same sheet, offering core packs.
- **Results:** when a run leaves you close to an upgrade (within about 20% of its
  price), one quiet line, "300 credits from thrust 4", with a link to top up.
- **Limit:** at most one store prompt per session that the player didn't ask for
  (the results line). The short-of sheets come only from a tap, so they don't
  count. Never during a run, the countdown or the revive offer.
- **The store screen** itself in the new look: credit packs and core packs side
  by side, the best value flagged, the starter pack and the pass, restore purchases.
- Log every prompt through the analytics events above (`view_store` with its source).
